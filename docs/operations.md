# 运维、排错与回退

## 日常开发与发布检查

已在本机验证的 Node 版本为 22.22.3，CI 固定使用该版本。首次克隆执行 `npm run install:ci`，按锁文件安装；日常快速验证执行 `npm run check:quick`，提交或发布前执行 `npm run check`。

完整检查依次运行：TypeScript、单元测试、生产构建、三角色业务集成、并发写入集成。集成脚本自动创建隔离的数据库和照片存储、启动独立端口，结束时停止测试服务并删除测试临时目录。不会对学校正在使用的数据做压力测试。日志中的实验性 SQLite 提示只涉及测试适配器。

可以单独执行 `npm test`、`npm run typecheck`、`npm run verify:roles`、`npm run verify:races`。角色和并发集成报告默认保存在项目父目录 `reports/verification-日期`；完整检查报告在 `reports/quality-日期`，也可用 `STABILITY_REPORT_DIR` 指定目录。`check:quick` 不含构建和业务集成，不能用来宣布完整检查通过。

GitHub 的 Quality checks 工作流在 main 提交和 PR 时运行完整检查，只使用生成的测试数据，不需要真实学生信息或生产密钥。报告作为附件保留 14 天；工作流不能替代线上监控。首次云端执行仍需查看 Actions 结果，本地通过不等于云端已经通过。

## 服务健康与故障定位

- `GET /api/health` 是公开的轻量存活检查，只表明应用能返回请求，不代表数据库、照片存储或登录均正常。
- 管理员登录后访问 `GET /api/health?ready=1`，检查数据库读取与照片存储读取。非管理员禁止访问。检查不写数据、不上传或删除照片，依赖探测最多等待约 1.5 秒后返回结果；身份校验本身的耗时不在这个窗口内。
- 就绪检查失败返回 503，只显示 `database`、`storage` 状态，不泄露错误堆栈或服务配置。超时只是停止等待，不能强制取消已经发出的底层数据库请求。
- 通用接口报错带 `requestId` 和 `X-Request-ID`，服务日志用相同编号关联；内部错误不把 SQL 或堆栈返回给页面。暂未接入集中日志平台，需在部署平台查询日志。
- 页面渲染错误提供恢复入口。刚提交过成绩、导入或照片时，先查询保存结果，再决定是否重做；不要因为网络报错连续点提交。

异常处理模块暂时兼容历史中文业务错误；新模块应使用有状态码和代码的 `HttpError`。JSON 接口按字节限制为 2,000,000 bytes，并在读取过程中截断过大请求；Excel 仍用已有分批导入，照片走原有独立大小和数量限制。

## 真实容量与上线条件

最近一次容量测试见 `tests/FULL-STABILITY-20261020.md`。其中 200 个集中登录客户端是 196 成功、4 个服务错误；不能宣传为 200 人同时登录全部可靠。本次不改变密码强度、登录队列和服务器资源，不重新作出容量承诺。

本机开发服务、电脑断电、网络中断、手机浏览器内存不足以及平台故障都可能导致不可用。“不会崩”的绝对保证做不到。正式使用应部署到持续运行的服务，使用 HTTPS，配置独立的可用性告警、资源与配额告警、访问日志保留、定期备份与恢复演练。当前尚未自动配置这些生产服务。

## 备份和恢复

GitHub 只保存源码。学生名单、成绩、账号数据库和照片存储不在仓库中，源码备份不能恢复它们。

正式部署后，按所用 D1/R2 或实际服务器的备份能力，定期保留数据库与照片对象的对应版本，并设置访问控制、保留期限和异地副本。先在独立环境验证恢复后的登录、各学院名单、成绩、归档、照片链接和下载，再考虑替换正式环境；记录恢复耗时和最近可恢复时间。这次没有替用户建立生产备份，也没有对真实业务数据执行恢复。

本地运行时数据在 `.wrangler/state`，不能在正在写入时简单复制单个 SQLite 文件当作可靠备份。维护前停服或使用数据库支持的一致性备份方式，并连同照片存储完整保留；不要把这个目录上传 GitHub。

2026-10-22 已补充 Windows 本机启动前自动备份、校验及独立目录恢复工具，详见 [本机业务数据备份与恢复](./data-backup.md)。该工具不代替线上备份、异地副本或定时备份。
