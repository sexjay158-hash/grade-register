# 并发压力测试

在项目目录运行 `npm run verify:load`。脚本先构建当前源码，在随机本地端口启动 Worker，使用单独的临时 D1/R2 目录；不会连接现有业务库或公网网站。测试入口拒绝缺少初始化口令或非本地目标的运行。

数据为 6000 名合成学生、10 个学院、200 个小组、1800 条种子成绩和 20 个测试人员账号。测试同时登录、已登录后的身份/学期/数据查询、不同活动同时改分、同版本争抢同一成绩、512 KiB 照片上传和压力后的恢复读取。查询验证学院与负责年级隔离，改分争抢必须只允许一个请求成功。

每个阶段采用无思考时间的闭环客户端，连续升压，阶段间不清空数据库或重启服务；前一阶段的排队可能影响后一阶段。请求超时为 15 秒，不自动重发；登录页面本身的提交超时为 20 秒，因此报告超时率不等同于页面的实际失败率。并发客户端数不能直接当作线上支持人数。

报告保存在项目上一级 `reports/concurrency-20261020.md` 和同名 JSON；报告和脚本保留供核对、复测。测试库在结束时删除，脚本启动的 Worker 会关闭。没有测试公网隧道、手机浏览器交互、手机 OCR 运算或云端 D1 配额。正式部署后须在隔离的预发布环境另测，不能将本地数据当作云端容量。

## 200 个独立账号突发测试

运行 `npm run verify:burst`。使用另外的独立数据库，预置 200 个不同账号及会话，每个账号使用独立随机盐和 600000 次 PBKDF2。通过真实登录接口同时验证 200 组账号密码，截止时间 20 秒。随后重启测试 Worker，取消残留密码计算，再用已验证的独立会话同时上传 200 张不同照片，每人一张、每张约 512 KiB，截止时间 30 秒，不执行 OCR。两阶段分开，结果不能当作 200 人同时登录并上传的混合容量。

账号、会话及临时 SQL 均只存在于测试目录，结束时清理。报告为上一级 `reports/concurrency-200-20261020.md` 和同名 JSON；成功照片需下载核对 SHA256，其他账号不得访问未归组照片。


## 稳定性与在线操作复测

运行 `node scripts/verify-burst.mjs --stability`，或已构建后加 `--skip-build`。沿用隔离库和 200 个不同账号的合成数据，先测 200 个在线会话分散读取，再让 200 个客户端同时调用真实前端登录等待函数，记录等待后的成功率和延迟，并在登录期间检查已有会话能否继续查询。只有明确的 LOGIN_BUSY 会自动等待重试，其他失败直接记为失败。随后测试 200 人同时上传每人一张 512 KiB 照片、下载哈希、跨账号权限，以及同一批次同时 36 张上传是否准确限制为 30 张。

在线场景每人读取三轮，每轮依次调用身份、学期、状态，轮间停顿 10–14 秒，初次进入分散在 12 秒内。此负载比正常页面 45–60 秒刷新更频繁，但没有模拟每个人一直修改成绩。默认报告保存在上级 reports/stability-20261020/stability.md、stability.json；可用 LOAD_REPORT_DIR 指定独立报告目录，不覆盖原突发测试基线。测试运行目录和合成凭据结束时删除，报告保留。运行期间不要另开重型压测，以免污染本机结果。

批次容量校验可用 `--stability-capacity --skip-build` 在全新隔离库单独复测，沿用同一报告中已经完成的在线/登录/200 张上传结果；只允许清除容量阶段的失败标记，不能覆盖其他阶段失败。原始失败报告应另存保留。该复测不重复集中登录，不代表新一轮全场景测试。
